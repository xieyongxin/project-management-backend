# 第一期开发执行规则

本文件是后续开发的执行约束，必须与 `doc/product/PRD-v1.md` 和 `doc/DECISIONS.md` 一起阅读。

## 1. 开发节奏

1. 每次只实现一个可独立验收的业务行为。
2. 编码前先说明本轮目标、验收条件和预计改动范围。
3. 常规技术细节沿用现有项目约定；产品决定必须向用户确认。
4. 不混入无关功能、无关重构或依赖升级。
5. 待确认决定不能被当作默认需求实现。

## 2. 安全和业务边界

1. 后端必须执行项目隔离和权限校验，前端按钮隐藏不能代替后端校验。
2. 私有附件、版本历史和项目日志也必须遵守项目访问边界。
3. 超级管理员身份不能自动绕过项目业务数据隔离。
4. 不得直接复用匿名可读的公共上传资源承载私有项目附件。
5. 不得把项目正文、附件解析内容或完整 AI 输入输出写入无项目边界的全局日志。

## 3. 数据库和迁移

1. 数据库采用版本化增量脚本。
2. 不重新初始化现有数据库。
3. 不使用会清空业务数据的迁移方式。
4. 新增表、字段、索引和数据修复必须可审查、可重复执行或明确不可重复执行原因。
5. 迁移前检查目标数据库现状，迁移后验证结构、索引和关键数据。

## 4. 验证规则

1. 验证要针对业务风险，不把编译成功当成功能完成。
2. 至少验证权限边界、项目隔离、非法 ID 访问、状态和版本行为、附件访问和日志泄露风险中与本轮目标相关的部分。
3. 验证通过后自动创建本地提交并继续，不逐轮等待批准。
4. 验证失败时不得声称功能完成，应记录失败原因和下一步。
5. 每轮更新 `doc/TASKS.md` 中的任务状态、验证结果和提交编号。

## 5. 双仓库和提交

1. 后端和前端独立提交，用相同任务编号关联。
2. 提交前分别检查两个仓库的 Git 状态和差异。
3. 不推送、不部署。
4. 不提交密钥、口令、临时配置、日志、构建产物或本地运行数据。
5. 保留用户已有改动，只提交本轮相关文件。
6. 提交信息应包含任务编号和简短行为描述。

## 6. 文档和交付

1. 编码前必须先读取：后端 `doc/product/PRD-v1.md`、`doc/DEVELOPMENT.md`、`doc/TASKS.md`、`doc/DECISIONS.md` 和当前仓库的 `AGENTS.md`。
2. 前端不复制 PRD；前端通过 `AGENTS.md` 引用后端仓库的唯一 PRD。
3. 每轮结束时说明完成行为、验收结果、改动文件、后端提交、前端提交和未解决问题。
4. 如发现文档与用户新决定冲突，暂停相关实现并更新 `DECISIONS.md`，不得自行选择。
